# 项目启动与配置指南

> 项目版本：2.3.0

本指南面向"把项目跑起来"这一个目标：讲清配置从哪来、两台机器上的两条容器化路线怎么选、首次启动会自动完成哪些事、以及跑不起来时按什么顺序排查。

- 想了解业务与架构，看《一体式志愿者服务平台设计方案》。
- 想查某个配置项的含义，看本文 §2。
- 想看接口，看《后端接口API文档》或运行时的 Swagger UI。

---

## 一、部署形态总览

### 1.1 两套编排文件

仓库根目录有两套互斥的 Compose 编排，**同一时间只用一套**：

| 文件 | 服务组成 | 顶层 `name` | 网络 | 卷 | 适用场景 |
|---|---|---|---|---|---|
| `docker-compose.env.yml` | MySQL + Redis + MinIO + 后端 | `volunteer-platform` | `volunteer-net` | `mysql-data`、`minio-data`、`redis-data` | 推荐。一条命令起全套，数据库也由容器提供 |
| `docker-compose.yml` | Redis + MinIO + 后端 + Nginx | 无 | `volunteer-network` | `redisdata`、`miniodata` | 已自有 MySQL（本机服务或远程实例），并希望用 Nginx 托管前端静态页 |

两套文件的差别只有两点：**MySQL 从哪来**、**有没有 Nginx**。后端镜像、后端环境变量、端口绑定方式完全一致。

> 两个文件都用了 `image: volunteer-backend:2.3.0` + `build: .`，所以 `docker compose -f <文件> up --build` 构建一次后，换另一个文件启动可复用同一镜像，不必重复构建。

### 1.2 端口与访问入口

所有宿主端口都**只绑定回环地址 `127.0.0.1`**，不对局域网开放（编排文件里的端口映射统一写成 `127.0.0.1:${变量:-默认值}:容器内端口`）。

| 服务 | 容器名 | 容器内端口 | 宿主绑定 | 覆盖用变量 | 默认值 | 出现在 |
|---|---|---|---|---|---|---|
| MySQL | `volunteer-mysql` | 3306 | `127.0.0.1:3306` | `MYSQL_PORT` | 3306 | 仅 env 编排 |
| Redis | `volunteer-redis` | 6379 | `127.0.0.1:6379` | `REDIS_PORT_HOST` | 6379 | 两套 |
| MinIO S3 API | `volunteer-minio` | 9000 | `127.0.0.1:9090` | `MINIO_API_PORT` | 9090 | 两套 |
| MinIO 控制台 | `volunteer-minio` | 9001 | `127.0.0.1:9091` | `MINIO_CONSOLE_PORT` | 9091 | 两套 |
| 后端 | `volunteer-backend` | 8081 | `127.0.0.1:8080` | `BACKEND_PORT` | 8080 | 两套 |
| Nginx | `volunteer-nginx` | 80 | `127.0.0.1:80` | `NGINX_PORT` | 80 | 仅 `docker-compose.yml` |

注意：**后端在容器内监听 8081，宿主侧通过 8080 访问**。8081 只存在于容器网络内部，宿主上并没有进程监听它。`SERVER_PORT=8081` 是后端自己的 `server.port`。

启动成功后可以访问的入口：

| 入口 | 地址 | 说明 |
|---|---|---|
| 前端页面 | `http://localhost/` | 仅 `docker-compose.yml`（Nginx）；需先构建前端产物，见 §3.2 |
| REST 接口 | `http://localhost/api/**` | 经 Nginx 转发；直连后端时为 `http://localhost:8080/api/**` |
| 健康检查 | `http://localhost/api/actuator/health` | 存活/就绪探针也可用 `/api/actuator/health/liveness`、`/api/actuator/health/readiness` |
| Swagger UI | `http://localhost/swagger-ui/index.html` | **不带 `/api`**；直连后端为 `http://localhost:8080/swagger-ui/index.html` |
| OpenAPI JSON | `http://localhost/v3/api-docs` | **不带 `/api`** |
| WebSocket | `ws://localhost/ws/**` | Nginx 已配置 `Upgrade` 头透传 |
| MinIO 控制台 | `http://localhost:9091` | 账号口令取 `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` |

关于 `/api` 前缀的来源：项目**没有设置** `server.servlet.context-path`，`/api` 是每个 Controller 自己在 `@RequestMapping` 里写的前缀；只有 Actuator 是通过 `management.endpoints.web.base-path=/api/actuator` 显式对齐的。所以 Swagger 系列路径（`/v3/api-docs`、`/swagger-ui/**`、`/doc.html`）**都不带 `/api`**，而业务接口都带。

### 1.3 前置依赖

| 依赖 | 版本要求 | 用途 |
|---|---|---|
| Docker Desktop（Windows/macOS）或 Docker Engine + Compose v2 | Compose v2（命令是 `docker compose`，不是 `docker-compose`） | 全部容器化路线 |
| Node.js + npm | 18 LTS 及以上（`package.json` 使用 Vite 5 / uni-app 3） | 构建前端产物，Nginx 路线必需 |
| JDK 17 + Maven | JDK 17；仓库自带 `mvnw` / `mvnw.cmd`，无需另装 Maven | 仅本机开发路线（§5） |
| 磁盘 | 首次构建镜像约 1.5～2 GB，Maven 依赖约 1.1 GB | 建议预留 ≥5 GB |

不需要预先安装 MySQL、Redis、MinIO——除非走 §4 的路线 B。

## 二、配置体系

### 2.1 一次配置的完整链路

```
.env（仓库根，唯一需要人工填写的文件）
   │  ① docker compose 自动读取根目录 .env，用于替换编排文件里的 ${VAR}
   ▼
编排文件的 environment: 段（容器环境变量）
   │  ② docker 把键值注入容器进程
   ▼
容器内环境变量
   │  ③ Spring Boot 的宽松绑定（relaxed binding）：环境变量优先级高于 application.yml 里的默认值
   ▼
application.yml / application-dev.yml / application-prod.yml 中的 ${VAR:默认值}
```

**四条铁律**（来自 `.env.example` 头部注释）：

1. **Spring Boot 不读 `.env`**。`.env` 只被 Docker Compose 和本机的 `scripts/load-env.ps1` 消费。没有经过这两者时，`.env` 里的值对应用完全不可见。
2. **`.env` 是唯一需要填写的敏感信息载体**。不要把真实口令写进 `.env.example`、`docker-compose*.yml`、`application*.yml` 或任何 Java 代码。
   - 唯一例外是本机开发用的 `application-local.yml`：它是被 `.gitignore` 忽略的**个人**文件，见 §2.6。
3. **`.env` 只在容器重建时生效**。改完 `.env` 必须 `docker compose -f <文件> up -d`（必要时加 `--force-recreate`）；单纯 `restart` 不会重新读取。
4. **本机跑后端不再需要先 source `.env`**（2026-02 起）。`application-dev.yml` 通过 `spring.config.import` 加载 `application-local.yml` 来提供 `jwt.secret` 与 `encrypt.secret-key`；环境变量仍然可用且优先级更高。注意这两个键已从 `application.yml` / `application-dev.yml` 中**移除**（不能留空默认值，否则会盖住导入文件），详见 §2.6。

### 2.2 准备 `.env`

```powershell
Copy-Item .env.example .env
```

然后按 §2.3 填写必填项。生成强随机密钥：

```powershell
.\scripts\gen-secrets.ps1                 # 仅打印新生成的 JWT_SECRET / ENCRYPT_SECRET_KEY
.\scripts\gen-secrets.ps1 -Apply          # 写回 .env（原文件备份为 .env.bak）
```

`gen-secrets.ps1` 只生成 `JWT_SECRET`（64 字符）与 `ENCRYPT_SECRET_KEY`（32 字符），字符集为 `A-Za-z0-9`，使用 `System.Security.Cryptography.RandomNumberGenerator`。数据库口令、MinIO 口令**不在**它的生成范围内，需手工填写。

> MinIO / MySQL 的 root 口令只在**首次创建数据卷**时生效。改了 `.env` 里的口令后如果卷已存在，必须 `docker compose ... down -v` 删除卷重新初始化（会清空数据），见 §6。

### 2.3 必填变量

编排文件里用 `${VAR:?提示}` 声明的变量**没有默认值**，缺失时 Compose 会直接报错拒绝启动：

| 变量 | 用途 | 备注 |
|---|---|---|
| `SPRING_DATASOURCE_URL_HOST` | 后端连宿主 MySQL 的 JDBC URL（`host.docker.internal` 形态） | 仅 `docker-compose.yml` 需要；`SPRING_DATASOURCE_URL` 变量名含冒号，不能用作 Compose 的默认值写法 |
| `SPRING_DATASOURCE_USERNAME` / `SPRING_DATASOURCE_PASSWORD` | 数据库账号口令 | 两套编排都需要 |
| `REDIS_PASSWORD` | Redis 口令 | 编排用 `${REDIS_PASSWORD:?}`；Redis 以 `--requirepass` 启动，不允许空口令 |
| `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` | MinIO 访问凭据 | 需与 `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` 一致 |
| `LLM_API_KEY` | 大模型密钥 | 留空**不影响启动**，只影响 `/api/ai/**` 调用（调用时才失败） |
| `JWT_SECRET` | JWT 签名密钥 | **必须 ≥32 字符**，不足会在启动期直接失败 |
| `ENCRYPT_SECRET_KEY` | 敏感字段 AES-256-GCM 密钥 | 至少 16 字符；**更换后历史已加密数据无法解密** |

其余变量都在编排文件里写了默认值，可留空。注意 `.env` **没有**定义 `BACKEND_PORT` / `NGINX_PORT` / `MYSQL_PORT` / `REDIS_PORT_HOST` / `MINIO_API_PORT`，因此宿主端口默认走 §1.2 表里的值。

### 2.6 本机开发密钥：`application-local.yml`

**适用场景**：前端/后端跑在宿主机（路线 §5），不想每次开终端都先 `source` 一遍 `.env`。

**机制**：`application-dev.yml` 顶部有一行导入声明，把编辑产物目录下的 `application-local.yml` 读进配置：

```yaml
spring:
  config:
    import: optional:classpath:application-local.yml
```

`optional:` 前缀表示文件不存在时不报错（静默跳过），因此对容器/CI 无任何影响。

**首次使用**：

```powershell
# 在仓库根执行（gen-secrets.ps1 的内部路径依赖脚本位置，会自行定位根目录 .env）
.\scripts\gen-secrets.ps1        # 可选：生成随机密钥，手工填入

Set-Location volunteer-backend\volunteer-server\src\main\resources
Copy-Item application-local.yml.example application-local.yml
# 然后用上一步输出的随机值替换文件里的两个 CHANGE_ME
```

`application-local.yml` 只需两个键：

```yaml
jwt:
  secret: <≥32 字符随机串>
encrypt:
  secret-key: <≥16 字符随机串，建议 32>
```

**优先级**（高 → 低）：

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | 环境变量 `JWT_SECRET` / `ENCRYPT_SECRET_KEY` | 宽松绑定（relaxed binding）直接映射到 `jwt.secret` / `encrypt.secret-key`，优先级高于所有配置文件。容器由 `docker-compose*.yml` 注入，本机可由 `load-env.ps1` 导入 |
| 2 | `application.yml` / `application-dev.yml` 等**声明文档** | 这两个文件**刻意不再写** `jwt.secret` / `encrypt.secret-key`（见下方"关键约束"） |
| 3 | `application-local.yml` | 由 dev 配置的 `spring.config.import` 导入，仅 dev profile 生效 |

**关键约束：为什么配置文件里不能写 `jwt.secret: ${JWT_SECRET:}`**

`spring.config.import` 导入的属性源优先级**低于声明它的文档**（Spring Boot 官方规则：imported files rank below the file that declares the import，但高于更早加载的文档）。因此如果 `application.yml` 或 `application-dev.yml` 里写了 `jwt.secret: ${JWT_SECRET:}`，那个**空字符串**会反过来盖住 `application-local.yml` 提供的真实密钥，本机未导入 `.env` 时依旧会报 `Could not resolve placeholder 'JWT_SECRET'` 或空密钥启动失败。这正是密钥改由 `application-local.yml` 承载时必须把两处绑定删掉的原因；环境变量仍然有效，因为它走的是宽松绑定而不是配置文件里的占位符。

回归测试：`volunteer-backend/volunteer-server/src/test/java/com/volunteer/server/LocalSecretsImportTest.java` 用固定夹具固化了上述导入、优先级、`optional:` 回落与占位值拒绝四条语义。

**安全约束**：

- 该文件已被 `.gitignore`（`**/application-local.yml`）与 `.dockerignore` 排除，不会入库、不会进镜像；`git status` 里不应看到它（只应看到 `application-local.yml.example`）。
- `.example` 模板里的示例值以 `CHANGE_ME` 开头，**原样复制不修改会导致启动失败**，避免"忘了替换、用公开密钥跑起来"这种静默高危配置。
- `prod` profile 不导入本文件，仍由 `application-prod.yml` 的 `${JWT_SECRET}`（无默认值）强制注入。
- 轮换 `encrypt.secret-key` 会导致历史已加密数据无法解密，必须配套数据迁移。

**验证是否生效**：

```powershell
Set-Location volunteer-backend\volunteer-server\src\main\resources
Select-String -Path application-dev.yml -Pattern "config" -Context 0,1
Select-String -Path application.yml,application-dev.yml -Pattern "^\s*(secret|secret-key):"
```

第一步应看到 `import: optional:classpath:application-local.yml`；第二步**不应有任何输出** —— 若仍能看到 `secret: ${JWT_SECRET:}`，说明源码或本地构建产物是旧的，配置处于"本机密钥被空值覆盖"的坏状态，先 `mvn -q clean` 重建。

## 三、路线 A：全套容器（`docker-compose.env.yml`）

推荐路线。在本机执行，目录为仓库根。

### 3.1 准备配置

```powershell
Copy-Item .env.example .env
.\scripts\gen-secrets.ps1 -Apply     # 生成并写入 JWT_SECRET / ENCRYPT_SECRET_KEY
```

按 §2.3 核对必填项；若想让 MySQL 容器使用非 root 账号，`MYSQL_USER` / `MYSQL_PASSWORD` 必须与 `SPRING_DATASOURCE_USERNAME` / `SPRING_DATASOURCE_PASSWORD` 一致。

### 3.2 构建前端产物（使用 Nginx 时必需，路线 A 可跳过）

`docker-compose.env.yml` 不含 Nginx，用后端 + 直连 8080 即可。若改用 `docker-compose.yml`，Nginx 会把 `./volunteer-frontend/dist/build/h5` 挂载为站点根目录，该目录**不在版本库中**，必须先构建：

```powershell
cd volunteer-frontend
npm ci
$env:VITE_API_BASE_URL='http://localhost'    # 经 Nginx 统一入口，见 §4.3
npm run build:h5
cd ..
```

产物落在 `volunteer-frontend/dist/build/h5/`，其中应有 `index.html`。构建脚本定义在 `volunteer-frontend/package.json`：`build:h5` = `uni build`。

### 3.3 启动

```powershell
docker compose -f docker-compose.env.yml up -d --build
```

首次会依次：拉取 `mysql:8.0`、`redis:7.4-alpine`、`minio/minio:latest`（这些来自 Docker Hub）→ 构建后端镜像（基础镜像 `eclipse-temurin:17-jdk-alpine` 与 `eclipse-temurin:17-jre-alpine`，构建过程执行 `./mvnw dependency:go-offline` 与 `./mvnw clean package -DskipTests`）→ 按 `depends_on` 顺序启动。

启动顺序由健康检查决定：**MySQL（`service_healthy`）→ MinIO（`service_started`）→ Redis（`service_healthy`）→ 后端**。MinIO 只等"已启动"是因为官方镜像里没有 `curl`，无法做健康检查。

构建耗时：镜像内不挂载宿主机的 `~/.m2`，首次需要完整下载 Maven 依赖（约 1.1 GB），通常十分钟以上；后续构建会命中 Docker 层缓存。

只重建后端（改了 Java 代码后）：

```powershell
docker compose -f docker-compose.env.yml up -d --build backend
```

### 3.4 首次启动会自动完成的事

| 事项 | 由谁完成 |
|---|---|
| 创建数据库 `volunteer_db` | MySQL 容器的 `MYSQL_DATABASE=volunteer_db`（**不是** Flyway；`docker-compose.env.yml` 的 MySQL 也没有挂载 `docker-entrypoint-initdb.d`） |
| 创建 70 张表、索引、外键、种子数据 | 后端启动时 Flyway 执行唯一迁移脚本 `volunteer-backend/volunteer-server/src/main/resources/db/migration/V1__baseline_full_schema.sql` |
| 创建 MinIO 桶 `volunteer` | 后端启动时的 `MINIO_AUTO_CREATE_BUCKET=true`（dev profile 亦为 `true`） |
| 创建初始账号 | 上述 V1 脚本内的种子数据，账号见 §3.5 |
| 建立初始权限/角色映射 | 同上 |

注意：`db/init.sql` 是供**手工**初始化用的同源脚本（内容与 V1 基线等价，额外包含种子数据），**Flyway 不会执行它**（Flyway 只扫 `classpath:db/migration`）。手工建库方式见 §4.1。

### 3.5 启动验证与初始账号

```powershell
docker compose -f docker-compose.env.yml ps            # 四个容器应为 running / healthy
docker compose -f docker-compose.env.yml logs -f backend
```

日志中应看到 Flyway 的迁移记录（`Successfully applied 1 migration`）与 `Started VolunteerApplication in ... seconds`。然后：

```powershell
Invoke-RestMethod http://localhost:8080/api/actuator/health
# {"status":"UP", ...}
```

## 四、路线 B：复用宿主机 MySQL（`docker-compose.yml`）

### 4.1 与路线 A 的差异

| 项 | 路线 A | 路线 B |
|---|---|---|
| MySQL | 容器 `volunteer-mysql` | **宿主机或远程实例，需自行准备** |
| 后端连接的库地址 | `SPRING_DATASOURCE_URL`（`mysql:3306` 容器名） | `SPRING_DATASOURCE_URL_HOST`（`host.docker.internal:3306`，编排已配 `extra_hosts: host.docker.internal:host-gateway` 以兼容 Linux） |
| Redis / MinIO | 容器 | 容器（同路线 A） |
| Nginx + 前端 | 无 | 有，需先构建前端产物（§3.2） |
| 建库建表 | 容器自动建库 + Flyway 建表 | **手工建库**（`CREATE DATABASE volunteer_db ...`，可用 `db/init.sql` 一次性建库建表灌种子）+ Flyway 迁移 |

手工初始化（在宿主机 MySQL 上，用 `db/init.sql`）：

```powershell
mysql -uroot -p < volunteer-backend\volunteer-server\src\main\resources\db\init.sql
```

或只建库、交给 Flyway 建表：

```sql
CREATE DATABASE IF NOT EXISTS volunteer_db
  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

两种做法前，先把 `docker-compose.yml` 需要的 `SPRING_DATASOURCE_URL_HOST` 指向宿主机 MySQL，并保证 `docker-compose.yml` 中该变量对应的库名与 `MYSQL_DATABASE` 语义一致（默认 `volunteer_db`）。

### 4.2 启动

```powershell
# 先确认宿主机 MySQL 已启动，且 .env 里 SPRING_DATASOURCE_URL_HOST 可连
docker compose -f docker-compose.yml up -d --build
```

服务顺序：Redis（健康）→ MinIO（已启动）→ 后端 → Nginx（等后端启动）。入口是 `http://localhost/`。

### 4.3 前端产物的 API 地址与 CORS

前端**不读运行时 `.env`**，但**也不需要**在构建期指定接口地址：生产构建（`uni build`，即 `npm run build:h5`）下 `request.js` 使用**同源相对路径** `/api/**`，由 Nginx 反代到后端，因此产物与部署域名解耦。

```bash
cd volunteer-frontend
npm ci
npm run build:h5        # 不需要设置 VITE_API_BASE_URL
```

`VITE_API_BASE_URL` 只影响**开发构建**（`npm run dev:h5`）：未设置时回退 `http://localhost:8081`；这时也可用 `vite.config.ts` 里已配置的 `/api`、`/ws` devServer 代理走同源。

| 场景 | 命令 | 页面来源 | 请求地址 | 是否跨域 |
|---|---|---|---|---|
| ① 经 Nginx 统一入口（推荐，生产） | `npm run build:h5` | `http://<host>[:NGINX_PORT]` | 同源 `/api/**` | 否 |
| ② 直连后端（不推荐） | `$env:VITE_API_BASE_URL='http://localhost:8080'; npm run build:h5` | 任意 | `http://localhost:8080/api/**` | 是，页面来源必须列在 `APP_CORS_ALLOWED_ORIGINS` |
| ③ 开发服务器 | `npm run dev:h5` | `http://localhost:5173` | devServer `/api` 代理或 `VITE_API_BASE_URL` | 走代理时同源 |

> 历史问题（已修复）：`request.js` 原先恒为 `import.meta.env.VITE_API_BASE_URL || 'http://localhost:8081'`，而构建流水线从不注入该变量，导致产物内被硬编码成 `http://localhost:8081`；远端浏览器打开页面时所有请求都打向**访问者自己的机器**，线上功能整体不可用。

CORS 白名单默认值是 `http://localhost:8080,http://localhost:3000,http://localhost:5173`。采用方案 ① 时请求同源，**不受** CORS 白名单约束；只有方案 ②（跨域直连）才需要把页面来源加进 `APP_CORS_ALLOWED_ORIGINS`。

## 五、本机开发路线（前端/后端跑在宿主机，中间件用容器）

中间件用 `docker-compose.yml` 的 Redis + MinIO 即可（不需要 Nginx）：

```powershell
docker compose -f docker-compose.yml up -d redis minio
```

**密钥准备（二选一）**：

- **推荐**：准备 `application-local.yml`（一次性，之后长期有效），见 §2.6。这样后面每次开发都不必再管密钥。

  ```powershell
  Set-Location volunteer-backend\volunteer-server\src\main\resources
  Copy-Item application-local.yml.example application-local.yml
  # 编辑 application-local.yml，把两个 CHANGE_ME 示例值换成随机串
  ```

- **兼容旧方式**：把根目录 `.env` 里的容器主机名改写为 `localhost` 并导入当前会话（每次开新终端都要执行）：

  ```powershell
  . .\scripts\load-env.ps1 -Local
  ```

`load-env.ps1` 的行为：从仓库根 `.env` 读取键值写入当前 PowerShell 进程的环境变量；`-Local` 会把 `//mysql:`、`//host.docker.internal:` 改写成 `//localhost:`，把 `REDIS_HOST=redis` 改成 `localhost`，把 `MINIO_ENDPOINT=http://minio:9000` 改成 `http://localhost:9090`；匹配 `PASSWORD|SECRET|API_KEY|ACCESS_KEY` 的键在打印时会脱敏（`-Quiet` 可静默）。其他参数：`-EnvFile <路径>`、`-Quiet`。环境变量优先级高于 `application-local.yml`，两者同时存在时以环境变量为准。

启动后端（`dev` profile）：

```powershell
.\mvnw.cmd -pl volunteer-backend/volunteer-server -am spring-boot:run
```

后端监听 `http://localhost:8081`。启动前需保证宿主机 MySQL 已建库（§4.1）：dev profile 的默认连接串指向 `localhost:3306`。

启动前端开发服务器：

```powershell
cd volunteer-frontend
npm ci
$env:VITE_API_BASE_URL='http://localhost:8081'
npm run dev:h5
```

其他常用脚本（`volunteer-frontend/package.json`）：`build:mp-weixin` / `dev:mp-weixin`（微信小程序）、`test`（`vitest run`）、`test:watch`、`test:coverage`。

后端测试与覆盖率门禁（JaCoCo 行覆盖 ≥60%、分支覆盖 ≥50%，仅在 `volunteer-server` 模块生效）：

```powershell
.\mvnw.cmd -pl volunteer-backend/volunteer-server -am test
```

## 七、故障排查

按下面的顺序排查，绝大多数问题会落在前四项。

### 7.1 拉取基础镜像失败（`registry-1.docker.io` 超时）

典型报错：

```
ERROR [internal] load metadata for docker.io/library/eclipse-temurin:17-jre-alpine
... dialing registry-1.docker.io:443: connect: connection timed out
... direct connection because Docker Desktop has no HTTPS proxy
```

原因：构建后端镜像需要 Docker Hub 上的 `eclipse-temurin:17-jdk-alpine` 与 `eclipse-temurin:17-jre-alpine`，当前网络到 `registry-1.docker.io` 不通，且 Docker daemon 未配置镜像加速器。**这与项目源码无关**，Maven 依赖（`repo.maven.apache.org`）通常仍然可达。

四种处理方式，任选其一：

1. **配置镜像加速器（推荐，永久生效）**：编辑 `C:\Users\<用户>\.docker\daemon.json`（Docker Desktop 也可在 Settings → Docker Engine 里改），加入
   ```json
   { "registry-mirrors": ["https://docker.m.daocloud.io"] }
   ```
   保存后重启 Docker Desktop。（实测可用的加速器会随时间变化，若失效需改用其他镜像站。）
2. **配置 HTTPS 代理**：Docker Desktop → Settings → Resources → Proxies。
3. **单次手工拉取并改标签**（不改任何项目文件）：
   ```powershell
   docker pull docker.m.daocloud.io/library/eclipse-temurin:17-jdk-alpine
   docker tag  docker.m.daocloud.io/library/eclipse-temurin:17-jdk-alpine eclipse-temurin:17-jdk-alpine
   docker pull docker.m.daocloud.io/library/eclipse-temurin:17-jre-alpine
   docker tag  docker.m.daocloud.io/library/eclipse-temurin:17-jre-alpine eclipse-temurin:17-jre-alpine
   ```
   之后重新 `up -d --build` 即可命中本地镜像。
4. **换用可直连的网络环境**。

> 注意：`eclipse-temurin:17-jdk-alpine` 与 `eclipse-temurin:17-jre-alpine` 必须是**真正的 Alpine 变体**。运行阶段会执行 `apk add --no-cache tzdata curl`，把 Ubuntu 变体（jammy/noble）改标签冒充 alpine 会导致该层直接失败。

### 7.2 页面空白 / 404

- 只有 `docker-compose.yml` 提供页面。`docker-compose.env.yml` **没有 Nginx**，访问 `http://localhost/` 本来就会失败——请直连 `http://localhost:8080/api/...`。
- 若用的是 `docker-compose.yml`：确认 `volunteer-frontend/dist/build/h5/index.html` 存在。该目录不入库，必须先执行 §3.2 的构建。目录为空时 Nginx 会返回默认欢迎页或 403/404。
- 构建后又改了接口地址：必须重新构建（地址是构建期内联的，不是运行时读取的）。

### 7.3 页面能打开但所有请求失败

- 打开浏览器开发者工具，看请求的实际地址。若是 `http://localhost:8081/...`，说明构建时没有设置 `VITE_API_BASE_URL`，命中了前端代码里的兜底值。按 §4.3 重新构建。
- 若报 CORS 错误：把页面来源加入 `APP_CORS_ALLOWED_ORIGINS` 并重建后端容器。
- 若返回 401：token 缺失或过期（响应体为 `{"code":401,"message":"token已过期"}`）。若返回 403 且提示"请先登录/权限不足/请先绑定学号"，是访问控制拦截器的正常拒绝。

### 7.4 后端启动即退出

按日志中的异常分类：

| 日志关键字 | 原因与处理 |
|---|---|
| `Unknown database 'volunteer_db'` | 库不存在。路线 A 由 `MYSQL_DATABASE` 自动建库；路线 B 需手工建库（§4.1） |
| `Access denied for user` | 数据库账号口令与 `SPRING_DATASOURCE_*` 不一致 |
| `Communications link failure` / `Connection refused` | 主机名或端口不对：容器内应用连 `mysql`/`redis`/`minio`，宿主机应用连 `localhost`。用错语境是最常见的原因 |
| `Table 'xxx' already exists` | 库里已有同名表但 `flyway_schema_history` 没有对应记录（例如先手工跑过 `init.sql` 再让 Flyway 迁移）。二选一：把手写建的表删掉让 Flyway 跑，或按《数据库设计文档》第六章的基线流程处理 |
| `Found non-empty schema ... without schema history table` | 同上，需要 `baseline-on-migrate=true`（dev 已是 `true`）或显式 `flyway baseline` |
| `JWT secret must be configured` / `JWT 签名密钥未配置` | 密钥完全没提供（`Could not resolve placeholder 'JWT_SECRET'` 是改造前的旧报错，现已不会出现）。本机开发：按 §2.6 创建 `application-local.yml`；容器：确认 `.env` 里的 `JWT_SECRET` 已填写且已 `up -d` 重建 |
| 已建好 `application-local.yml` 仍报上一行错误 | 配置文件里被写回了 `jwt.secret: ${JWT_SECRET:}`：导入文件优先级低于声明文档，空默认值会盖住本地密钥。按 §2.6「验证是否生效」两段命令检查，应为**无输出** |
| `JWT 签名密钥长度不足 32` / `JWT secret must be at least 32 characters` / `encrypt.secret-key 长度不足` | `JWT_SECRET` 或 `ENCRYPT_SECRET_KEY` 太短（JWT ≥32 字符、加密 ≥16 字符）。用 `.\scripts\gen-secrets.ps1 -Apply` 重新生成后填入 `.env` 或 `application-local.yml` |
| `jwt.secret 仍是 application-local.yml.example 中的示例值` | 只复制了模板没替换示例值。生成随机串填入 `application-local.yml` 的 `jwt.secret` |
| `encrypt.secret-key 未配置` | 同上，缺的是加密密钥；两者可以一起在 `application-local.yml` 里补齐 |
| `NOAUTH Authentication required` / Redis 认证失败 | `REDIS_PASSWORD` 与 Redis 容器 `--requirepass` 不一致，或用了空的默认值 |
| `Ports are not available` / `bind: 0.0.0.0:3306` | 宿主端口被占用。改 `.env` 中对应的 `*_PORT` 变量（如 `MYSQL_PORT`、`REDIS_PORT_HOST`），或释放占用端口 |
| `could not find or load main class` / 构建失败 | 看构建日志里 Maven 的报错；常见是网络问题导致依赖下载失败，重试或配置 Maven 镜像 |

### 7.5 功能层面的常见问题

| 现象 | 原因 |
|---|---|
| 上传大文件返回 413 | **Nginx 的 `client_max_body_size` 未设置**，默认只放行 1 MB，而后端上限是 50 MB。经 Nginx 上传大文件会先被 Nginx 拒绝。直连后端（8080）不受影响 |
| `/api/ai/**` 全部报错 | `LLM_API_KEY` 为空或无效。不影响应用启动，只在调用时失败 |
| 短信验证码收不到 | dev profile 使用 `console` 提供者，验证码只打印在后端日志里；生产需接入真实短信服务 |
| Swagger 页面 404 | 路径写成了 `/api/swagger-ui/index.html`。正确路径**不带 `/api`**：`/swagger-ui/index.html`、`/v3/api-docs` |
| MinIO 上传报桶不存在 | `MINIO_AUTO_CREATE_BUCKET=false`（prod 或主配置默认）且桶未预建；改为 `true` 或手工在 `http://localhost:9091` 建桶 `volunteer` |
| 改了 MinIO/MySQL root 口令没生效 | 数据卷已存在，口令只在首次初始化时生效。需 `down -v` 重建卷（会丢数据） |
| 时间显示差 8 小时 | 各容器与后端依赖 `TZ=Asia/Shanghai`。确认该变量未被覆盖；JDBC URL 也带 `serverTimezone=Asia/Shanghai` |
