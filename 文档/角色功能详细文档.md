# 角色功能详细文档

> 项目版本：2.3.0

本文回答一个问题：**系统中的每个角色，到底能做什么、不能做什么，以及这些限制是由哪一段代码保证的。**

内容包括：权限模型的三条判定链路、注解语义、五个角色的能力边界（附端点级清单）、数据可见性规则、前端的角色处理现状，以及权限体系目前存在的已知缺口。

接口的完整参数与返回体见《后端接口API文档》；角色的数据库表结构见《数据库设计文档》。

## 一、权限模型

### 1.1 三条判定链路

请求进入后端后，依次经过三道关卡。理解"某接口需要什么权限"必须把三道都看完——**只看注解会得出错误结论**。

| 顺序 | 组件 | 位置 | 职责 | 失败表现 |
|---|---|---|---|---|
| ① | `SecurityConfig` | `volunteer-backend/volunteer-auth/src/main/java/com/volunteer/auth/config/SecurityConfig.java:42-69` | 判断"是否已登录"。白名单外的所有请求都要求通过 JWT 认证 | HTTP 401（由 `JwtAuthenticationFilter` 写出裸 JSON） |
| ② | `AccessControlInterceptor` | `volunteer-backend/volunteer-auth/src/main/java/com/volunteer/auth/interceptor/AccessControlInterceptor.java` | 读取方法上的 `@RequiresPermission` / `@RequiresAccess` 注解，做角色与权限码判定 | HTTP 403，响应体是 `Result.error(message)` 的 JSON |
| ③ | Service 内业务校验 | 各 Service，如 `volunteer-backend/volunteer-activity/src/main/java/com/volunteer/activity/service/ActivityService.java:1001-1046` | 学院归属、审核资格、数据归属等业务级判定 | 通常是 HTTP 200 + `Result.error(msg)`（`BusinessException`），或抛 `IllegalArgumentException` → HTTP 400 |

第 ② 关的关键规则：**同时没有两个注解的方法一律放行**，只受第 ① 关约束（即"仅需登录"）。这一点写在 `AccessControlInterceptor.java:35` 的类注释里。

### 1.2 两个注解的语义

| 注解 | 定义位置 | 参数 | 语义 |
|---|---|---|---|
| `@RequiresAccess` | `volunteer-backend/volunteer-auth/src/main/java/com/volunteer/auth/annotation/RequiresAccess.java:8-13` | `String value() default "visitor"`、`boolean requireStudentId() default false` | 按**角色字符串**判定。`@Target(METHOD)` |
| `@RequiresPermission` | `volunteer-backend/volunteer-auth/src/main/java/com/volunteer/auth/annotation/RequiresPermission.java:20-31` | `String[] value() default {}`、`boolean requireStudentId() default false` | 按 **`sys_permission.permission_code`** 判定，数组为 **OR** 语义。`@Target({METHOD, TYPE})` |

优先级：`@RequiresPermission` **先于** `@RequiresAccess` 判定（`AccessControlInterceptor.java:66-76`）。

`@RequiresAccess` 的 `value` 取值与实际判定（`AccessControlInterceptor.java:112-155`）：

| `value` | 判定条件 | 不通过时的文案 |
|---|---|---|
| `"admin"` | `userService.checkIsAdmin(userId)` → `sys_user_role` JOIN `sys_role` 后存在 `role_code = 'ADMIN'` | 权限不足 |
| `"organizer"` | `checkIsAdmin(userId) \|\| userService.checkIsOrganizer(userId)`（`role_code = 'ORGANIZER'`） | 权限不足 |
| `"full"` | `authService.hasFullAccess(userId)` → `sys_user.access_level == 1` | 请先绑定学号以获得完整访问权限 |
| `"visitor"`（默认值） | **代码中没有 visitor 分支**，等价于"仅校验是否登录" | 请先登录 |
| 任意值 + `requireStudentId=true` | 在上述判定之外，额外要求 `access_level == 1` 或是 ADMIN | 请先绑定学号 |

`@RequiresPermission` 的判定（`AccessControlInterceptor.java:79-110`）：先校验登录（否则"请先登录"），再按需校验学号（否则"请先绑定学号"），`value()` 为空则直接放行；否则调用 `userPermissionService.loadPermissionCodes(userId)` 取出该用户的权限码集合，`Arrays.stream(required).anyMatch(userPerms::contains)` 命中即放行，否则"权限不足"。

**注意：`@RequiresPermission` 在主源码中零使用。** 全仓库唯一的使用处是测试文件 `volunteer-backend/volunteer-auth/src/test/java/com/volunteer/auth/interceptor/AccessControlInterceptorTest.java:133`。也就是说，细粒度权限模型（`sys_permission` / `sys_role_permission` / 15 个权限点 / Redis 缓存）**已经实现完整但尚未接入任何生产接口**，实际鉴权全部依赖 `@RequiresAccess` 的角色字符串。

### 1.3 认证与令牌

- 登录成功后由 `JwtUtil`（`volunteer-backend/volunteer-auth/src/main/java/com/volunteer/auth/util/JwtUtil.java`）签发 HS256 令牌，claims 含 `userId` 与 `username`，有效期 `jwt.expiration`（默认 `86400000` 毫秒 = 24 小时）。
- 客户端在请求头携带 `Authorization: Bearer <token>`。
- `JwtAuthenticationFilter`（`volunteer-backend/volunteer-auth/src/main/java/com/volunteer/auth/filter/JwtAuthenticationFilter.java`）校验通过后，把 `userId`（Long）与 `username`（String）写入 request 属性，供后续拦截器与 Controller 的 `@RequestAttribute` 读取。
- 令牌过期 → HTTP 401 + `{"code":401,"message":"token已过期"}`；令牌非法 → HTTP 401 + `{"code":401,"message":"token无效"}`。
- 无令牌时不拦截，直接放行到第 ① 关的白名单判定；不在白名单则 401。

免登录白名单（`SecurityConfig.java:42-68`，按声明顺序）：

| 匹配 | 方法 |
|---|---|
| `/**` | OPTIONS（预检请求） |
| `/api/auth/user/check-student-id`、`/api/college/list`、`/api/activity/page`、`/api/activity/list` | GET |
| `^/api/activity/\d+$`（正则，活动详情） | GET |
| `/api/auth/login`、`/api/auth/register`、`/api/captcha/**` | 不限 |
| `/api/actuator/health`、`/api/actuator/health/**`、`/api/actuator/info` | 不限 |
| `/doc.html`、`/swagger-resources/**`、`/webjars/**`、`/v3/api-docs/**`、`/swagger-ui/**` | 不限 |

**白名单里没有任何 `/api/file/**`、`/api/export/**` 条目**——文件上传/下载与报表导出都需要登录。

### 1.4 档案完整度门控（HTTP 460）

除注解之外还有一道与角色正交的门控：`ProfileCompletenessInterceptor`（`volunteer-backend/volunteer-auth/src/main/java/com/volunteer/auth/interceptor/ProfileCompletenessInterceptor.java`）。

- 受保护路径：`/activity/`、`/attendance/checkin`（`PROTECTED_PATHS`，`:28-31`），且仅当 URI 含 `/register` 或 `/checkin` 时才继续判定（`:48-55`）。
- 判定条件：`sys_user.profile_complete` 为 null 或 0 时拒绝。
- 拒绝方式：**HTTP 460** + `Result.error(460, "请先完善个人档案资料后再进行操作")`。
- 注册在 `volunteer-backend/volunteer-server/src/main/java/com/volunteer/config/WebMvcConfig.java:18-26`，与限流拦截器一起覆盖 `/api/activity/**` 与 `/api/attendance/**`。

460 是自定义状态码，前端 `volunteer-frontend/src/utils/request.js:42-49` 对它专门处理：当前页是管理端主页时，`uni.$emit('admin:open-profile-drawer')` 直接弹出"完善档案"抽屉；`STUDENT_ID_REQUIRED` 同理对应"绑定学号"抽屉。

### 1.5 角色与权限的存储

角色的权威来源是 **`sys_user_role` JOIN `sys_role`**，不是 `sys_user.role_code` 冗余列：

```java
// volunteer-backend/volunteer-auth/src/main/java/com/volunteer/auth/service/UserService.java:181-189
public boolean checkIsOrganizer(Long userId) {
    List<SysRole> roles = getUserRoles(userId);
    return roles.stream().anyMatch(role -> "ORGANIZER".equals(role.getRoleCode()));
}

public boolean checkIsAdmin(Long userId) {
    List<SysRole> roles = getUserRoles(userId);
    return roles.stream().anyMatch(role -> "ADMIN".equals(role.getRoleCode()));
}
```

代价是每个需要角色判定的请求都会查两次库（`sys_user_role` + `sys_role`），没有缓存。这是当前实现的一个性能特征。

`SysUser.getRoleCode()`（`sys_user.role_code` 冗余列）只在少数由 Service 自行推断角色的地方被读到，例如 `ActivityService.java:1085-1112` 的 `getUserRoleCode` / `:1114-1122` 的 `hasUserRole`；这些方法在字段为 NULL 时回退到按优先级列表推断或按 studentId 推断（回退 SQL 见 `:1124-1140`）。

### 1.6 细粒度权限（已实现、未启用）

`UserPermissionService`（`volunteer-backend/volunteer-auth/src/main/java/com/volunteer/auth/service/UserPermissionService.java`）是权限码链路的核心：

- `CACHE_TTL_MINUTES = 5L`、`CACHE_KEY_PREFIX = "user:perm:"`（`:32-33`）。
- `loadPermissionCodes(userId)`（`:41-69`）：userId 为 null 返回空集；命中 Redis 则按 `,` 切分返回；Redis 读异常只记 `log.warn("Redis 读取权限缓存失败,降级到数据库 userId={}")` 并落库查询；**查询结果为空集时不写缓存**（避免缓存穿透把空值固化 5 分钟）；否则写入 Redis 5 分钟，写异常同样降级为 warn。
- `evict(userId)`（`:74-83`）：删除缓存键——改角色/权限后需要调用它，否则最长 5 分钟后才生效。
- `loadFromDb(userId)`（`:85-95`）：`selectRoleIdsByUserId` → `selectPermissionCodesByRoleIds` → `Collectors.toSet()`。

## 二、角色定义

### 2.1 五个角色

种子数据 `volunteer-backend/volunteer-server/src/main/resources/db/migration/V1__baseline_full_schema.sql`（`db/init.sql` 同源）：

| id | `role_code` | `role_name` | 定位 | 学院绑定要求 |
|---|---|---|---|---|
| 1 | `ADMIN` | 超级管理员 | 系统超级管理员，拥有所有权限 | 不要求（天然跨学院） |
| 2 | `ORGANIZER` | 活动组织者 | 只能管理本院活动 | **必须绑定学院**，否则发起操作时抛"组织者必须绑定学院" |
| 3 | `VOLUNTEER` | 志愿者 | 报名参加活动 | 需绑定学号才能报名/签到（`access_level=1`） |
| 4 | `COLLEGE_ADMIN` | 学院管理员 | 管理本学院的志愿者活动 | 需绑定学院 |
| 5 | `AUDITOR` | 系统审核员 | 审核活动与用户 | 不要求 |

`sys_role.role_code VARCHAR(64) NOT NULL UNIQUE`，另有 `INDEX idx_role_code`。

### 2.2 十五个权限点

`sys_permission` 种子（id 即表中自增值，父子关系由 `parent_id` 表达）：

| id | parent_id | `permission_code` | 名称 |
|---|---|---|---|
| 1 | 0 | `system` | 系统管理 |
| 2 | 1 | `system:user` | 用户管理 |
| 3 | 1 | `system:role` | 角色管理 |
| 4 | 0 | `activity` | 活动管理 |
| 5 | 4 | `activity:list` | 活动列表 |
| 6 | 4 | `activity:audit` | 活动审核 |
| 7 | 4 | `activity:create` | 活动创建 |
| 8 | 0 | `attendance` | 考勤管理 |
| 9 | 8 | `attendance:checkin` | 签到管理 |
| 10 | 8 | `attendance:supplement` | 补签审核 |
| 11 | 0 | `report` | 报表统计 |
| 12 | 10 | `report:personal` | 个人报表 |
| 13 | 10 | `report:organization` | 组织报表 |
| 14 | 0 | `notification` | 消息中心 |
| 15 | 0 | `ai` | AI智能助手 |

> 第 12、13 条的 `parent_id` 都是 10（`attendance:supplement`），与"报表"语义不符——这是种子数据里的既有瑕疵，不影响功能（该字段目前无消费方）。

### 2.3 角色-权限映射

`sys_role_permission` 种子：

| 角色 | 授予的 `permission_id` | 含义 |
|---|---|---|
| `ADMIN` | 全部（`SELECT 1, id FROM sys_permission`） | 全部权限 |
| `ORGANIZER` | 4、5、7 | 活动管理、活动列表、活动创建 |
| `VOLUNTEER` | 10、12 | 补签审核、个人报表 |
| `COLLEGE_ADMIN` | 4、5、6、7、9、11、12 | 活动管理/列表/审核/创建、签到管理、报表统计、个人报表 |
| `AUDITOR` | 5、6、13 | 活动列表、活动审核、组织报表 |

由于 `@RequiresPermission` 未接入生产代码，**这张映射表目前不参与任何运行时判定**；上表的实际权限由下节的注解与 Service 校验决定。

### 2.4 内置账号

| 用户名 | 初始口令 | 角色 | 绑定学院 |
|---|---|---|---|
| `admin` | `Admin@2026Safe` | ADMIN | 系统管理部 |
| `organizer` | `Organizer@2026` | ORGANIZER | 志愿者协会 |
| `volunteer1` / `volunteer2` / `volunteer3` | `Volunteer@2026` | VOLUNTEER | 计算机学院 / 软件学院 / 信息学院 |
| `college_admin1` / `college_admin2` | `College@Admin2026` | COLLEGE_ADMIN | 计算机学院 / 软件学院 |
| `auditor` | `Auditor@2026` | AUDITOR | 系统管理部 |

口令以 BCrypt（strength 12）存储。全部账号 `status = 1`。学号仅 `volunteer1/2/3` 预置（2024001/2024002/2024003），其余账号需自行绑定。

> `access_level` 字段的 DDL 注释写的是"0-管理员, 1-组织者, 2-完整用户, 3-访客"，与代码中的 `AccessLevelEnum`（`VISITOR(0)`、`FULL_ACCESS(1)`）**直接矛盾**。以代码为准：只有 0 与 1 有意义，且语义是"0=未绑学号的访客、1=已绑学号的完整用户"。

## 三、各角色能力边界

### 3.1 判定语义速查

| 注解写法 | 通过者 |
|---|---|
| `@RequiresAccess("admin")` | 仅 ADMIN |
| `@RequiresAccess("organizer")` | ADMIN 或 ORGANIZER（**COLLEGE_ADMIN 不通过**） |
| `@RequiresAccess(requireStudentId = true)` | 已绑学号的用户（`access_level=1`）或 ADMIN |
| `@RequiresAccess("visitor")` | 任意已登录用户 |
| 无角色注解 | 任意已登录用户（可能再受 Service 层二次校验） |

一个容易踩的坑：`ActivityController` 的活动增删改/发布端点标的是 `@RequiresAccess(value="organizer", requireStudentId=true)`，而 `checkIsOrganizer` 只认 `role_code = 'ORGANIZER'`。**因此学院管理员（COLLEGE_ADMIN）在注解层就被拒绝了**，尽管 `ActivityService` 的 `validateCollegeAccess` 里专门写了 collegeAdmin 分支（`ActivityService.java:1025-1046`）。也就是说，学院管理员设计上"管理本学院活动"的写能力，被注解层挡住了，只剩审核分支可用。

| `POST /api/activity/{id}/audit` | `:117-118` |

**已知缺口**：`GET /api/activity/audit/page` 既无注解，Service 层 `getAuditActivityPage`（`ActivityService.java:569-572`）也只是复用 `getActivityPage(status=AUDITING)`，**没有按审核权限过滤**。因此任意登录用户都能拉到待审活动列表（虽然无法执行审核动作）。详见 §5。

### 3.5 志愿者（VOLUNTEER）与已绑学号的完整用户

| 能力 | 端点 | 判定 |

### 3.6 访客（VISITOR）与未登录（GUEST）

- VISITOR 由 `access_level == 0` 决定，能力等于"已登录但未绑学号"：可浏览公开活动、可调用无注解的读接口，不能报名、组队、签到（触发"请先绑定学号"）。
- GUEST（无 JWT）只能访问 §1.3 的白名单路径。
- 前端 `volunteer-frontend/src/utils/auth.js:51-58` 为 GUEST 定义了权限集 `['view_public_activities']`，但该映射没有被任何路由或页面守卫强制执行。

## 四、数据可见性规则

1. **学院隔离**：活动的写操作与审核按 `sys_activity.college_id` 与当前用户的 `college_id` 比对（`validateCollegeAccess` / `requireAuditPermission`）。ADMIN 不受此限制。
2. **范围隔离**：`activity_scope = UNIVERSITY` 的活动对所有人可见；`COLLEGE` 范围只对**本学院的完整用户**可见（`ActivityService.java:243-262`）。
3. **本人数据**：课表、待办、个人报表、信用流水等以 `user_id = 当前登录用户` 为唯一过滤条件，不存在"管理员查看他人课表"的接口（课表模块详见《一体式志愿者服务平台设计方案》课程表专章）。
4. **越权记录**：学院越权会被记入 WARN 日志（`log.warn("越权拦截: ...")`），便于事后审计。

## 五、已知缺口与风险

按影响程度排序。这些都是**代码现状**，不是设计意图。

1. **细粒度权限未接入**：`@RequiresPermission` 与 `UserPermissionService`（含 15 个权限点、Redis 5 分钟缓存、`evict` 方法）在主源码零调用。`sys_permission` / `sys_role_permission` 两张表与种子数据不参与任何运行时判定；`user:perm:*` 缓存键在生产中永远不会被写入。实际鉴权完全依赖 `@RequiresAccess` 的角色字符串。
2. **导出/下载接口无权限校验**：`/api/file/**` 与 `/api/export/**` 既不在 `SecurityConfig` 白名单，也没有任何 `@RequiresAccess` / `@RequiresPermission` 注解 → 拦截器一律放行。**任何已登录用户都能下载任意活动/报表的导出文件与上传文件**。旧版《后端接口API文档》曾把这些接口描述为"匿名白名单"或"受权限保护"，两种说法都不对。
3. **待审列表未过滤**：`GET /api/activity/audit/page` 无注解，Service 亦未按审核权限过滤，任意登录用户可读取待审活动分页。
4. **学院管理员写能力被注解层堵死**：`ActivityController` 的活动写端点只认 `ORGANIZER`，与 `validateCollegeAccess` 里的 collegeAdmin 分支自相矛盾。
5. **前端角色链断裂**：`LoginResponse`（`volunteer-backend/volunteer-auth/src/main/java/com/volunteer/auth/dto/LoginResponse.java:10-23`）与 `GET /api/auth/user/info`（`AuthController.java:81-96`）都**不返回 role / roleCode**；前端 `pages/login/index.vue:105` 的 `profile.role || loginData.role || loginData.roleCode` 三项恒为空，`normalizeRole`（`stores/user.js:7-9`）永远回退 `'VOLUNTEER'`，导致 `isAdminRole` / `checkAdmin()` 运行时恒为 false。
6. **前端无任何角色门控**：登录后统一 `uni.reLaunch('/pages/index/index')`（`pages/login/index.vue:150`）；管理端首页七个分区（运营概览/活动管理/用户学院/考勤失信/统计报表/公告发布/审计日志，`pages/index/index.vue:928-936`）对所有角色可见，`v-for` 无 `v-if` 门控；`App.vue` 仅 16 行、`script setup` 为空，没有路由守卫。页面上展示的角色标签来自上面那条恒为 `VOLUNTEER` 的值。
7. **无角色码常量类**：`"ADMIN"` / `"ORGANIZER"` / `"COLLEGE_ADMIN"` / `"AUDITOR"` / `"VOLUNTEER"` / `"VISITOR"` 以字符串字面量散落在 `ActivityService.java:982,986,994,998,1094-1103,1109,1111`、`ActivityImportServiceImpl.java:612`、`UserService.java:183,188` 及两个测试文件。拼错不会被编译器发现。
8. **`access_level` 注释与实现矛盾**：`V1__baseline_full_schema.sql` 中该列注释为"0-管理员, 1-组织者, 2-完整用户, 3-访客"，与 `AccessLevelEnum`（0=访客、1=完整访问）相反。
9. **角色判定无缓存**：每次 `@RequiresAccess("admin"/"organizer")` 都要查 `sys_user_role` + `sys_role`。高并发下会成为数据库热点。
10. **admin 的 `sys_user.role_code` 冗余列未回填**（种子脚本只回填了其余角色），依赖该字段的推断路径（`ActivityService.getUserRoleCode` / `hasUserRole`）对 admin 会退化到优先级列表或 studentId 推断。`checkIsAdmin` 走关系表，不受影响。

## 六、扩展权限的正确改法

若要让权限体系按设计意图工作，需要的改动（**当前代码未做**，仅作为后续演进的指引）：

1. 给接口补 `@RequiresPermission("permission:code")`，从最小的写操作开始（如 `activity:create` 对应活动创建）。
2. 在修改用户角色或角色权限后调用 `userPermissionService.evict(userId)`，否则最长 5 分钟后才生效。
3. 新增角色时同步补三处：`sys_role` 一行、`sys_role_permission` 若干行、以及引用该 `role_code` 的 Service 判定（因为角色码是字面量，没有常量类兜底）。
4. 若要修 §5.5 的前端角色链，需要在 `LoginResponse` 与 `/api/auth/user/info` 的返回体中补 `role` / `roleCode` 字段（数据取自 `sys_user_role JOIN sys_role`），前端才能据此做入口门控。
