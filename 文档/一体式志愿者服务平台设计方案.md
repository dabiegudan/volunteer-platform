## 一、项目概述

### 1.1 定位

一体式志愿者服务平台面向高校志愿服务场景，把"发布活动—招募志愿者—现场考勤—时长核算—激励与报表"这条线上闭环做成一个系统。技术形态是**前后端分离 + 多模块 Maven 单体**：后端一个 Spring Boot 应用（8 个 Maven 模块），前端一个 uni-app（Vue 3）应用，通过 REST + JWT 交互，可选接入大模型提供智能问答、活动推荐、内容生成与排班建议。

"一体式"的含义在于**不再按院系/组织分散到多个工具**：活动、报名、组队、考勤、时长、信用、证书、报表与消息在同一个数据模型下贯通，学院维度通过 `college_id` 做数据隔离，而不是各建一套系统。

### 1.2 核心业务场景

| 场景 | 参与角色 | 系统提供的能力 |
|---|---|---|
| 发布志愿活动 | 组织者、学院管理员 | 活动草稿、提交审核、审核通过、发布、取消、紧急活动直发、批量导入 |
| 招募志愿者 | 志愿者 | 活动列表/详情（含公开访问）、报名申请、组织者审核 |
| 组队参与 | 志愿者 | 建队、入队、队伍成员管理 |
| 现场考勤 | 志愿者、组织者 | 签到二维码、位置校验、补签申请与审核 |
| 时长核算 | 组织者、管理员 | 服务时长登记、时长争议、时长审批、外部平台时长导入 |
| 激励体系 | 志愿者 | 学分/信用分、徽章、每日任务、信用商品兑换、时间银行存取 |
| 报表与导出 | 各类管理员 | 个人/组织报表、统计看板、Excel/PDF 导出（异步任务） |
| 消息触达 | 所有人 | 站内信、公告、WebSocket 实时推送、短信（可插拔） |
| 智能助手 | 所有人 | 问答、活动推荐、活动草稿生成、总结与情感分析、排班建议 |

### 1.3 设计目标

1. **闭环**：报名、考勤、时长、报表共享同一份活动与用户数据，避免手工对账。
2. **可隔离**：校级（`UNIVERSITY`）与院级（`COLLEGE`）活动范围分离，学院管理员与组织者只能操作本院数据。
3. **可审计**：活动状态变更留 `activity_change_log`，后台操作留 `sys_operation_log`，越权尝试写 WARN 日志。
4. **可降级**：Redis 不可用时限流与权限缓存降级放行/落库（`RateLimitInterceptor:35-38`、`UserPermissionService:52`），AI 不可用时不影响主流程。
5. **容器化交付**：一条 `docker compose` 命令拉起全部依赖，配置集中在根目录 `.env`。

### 1.4 非目标

- 不做多租户（`college_id` 是数据隔离维度，不是租户隔离）。
- 不做微服务拆分——8 个模块最终打成**一个 jar**，模块化只是编译期边界。
- 不做分布式会话：认证是无状态 JWT，`SessionCreationPolicy.STATELESS`。
- 前端不做 SSR/独立 Web 站点：产物是 uni-app 的 H5（可再编到微信小程序）。

## 二、业务全景

### 2.1 主流程

```
组织者                          系统                             志愿者
  │                              │                                 │
  ├─ 创建活动 ─────────────────► DRAFT                             │
  ├─ 提交审核 ─────────────────► AUDITING                           │
  │                    ┌─────────┴─────────┐                        │
  │             审核通过│                 │审核拒绝                 │
  │                    ▼                 ▼                        │
  │                 APPROVED          REJECTED                     │
  ├─ 发布 ─────────────────────► RECRUITING ◄──── 浏览活动 ────────┤
  │                              │            ◄──── 报名申请 ───────┤
  │◄──────── 审核报名 ───────────┤                                 │
  │                              │                                 │
  │  （到开始时间，定时任务或手动）│                                 │
  │                              ▼                                 │
  │                           ONGOING ◄──── 扫码签到/补签 ─────────┤
  │                              │                                 │
  │  （到结束时间）               ▼                                 │
  │                           COMPLETED ──► 服务时长入账 ──────────► 时长/信用/报表
  │                              ▼                                 │
  │                           ARCHIVED                             │
  └─ 任意非终态可取消 ────────► CANCELLED                            │
```

### 2.2 活动状态机

状态定义在 `volunteer-backend/volunteer-common/src/main/java/com/volunteer/common/enums/ActivityStatusEnum.java`（10 个取值），流转全部由 `volunteer-backend/volunteer-activity/src/main/java/com/volunteer/activity/service/ActivityService.java` 控制，每个迁移都先校验当前状态、不满足则抛 `BusinessException`：

| 迁移 | 触发方法 | 前置状态 | 行号 | 前置不满足时的提示 |
|---|---|---|---|---|
| → `DRAFT` | `createActivity` | — | `:314` | 同名活动已存在 / 人数上限须大于 0 |
| → `AUDITING` | `submitForAudit` | `DRAFT` | `:338-342` | 只有草稿状态的活动才能提交审核 |
| → `APPROVED` | `approveActivity` | `AUDITING` | `:355-359` | 活动当前状态无法审核 |
| → `REJECTED` | `rejectActivity` | `AUDITING` | `:379-383` | 活动当前状态无法审核 |
| → `RECRUITING` | `publishActivity` | `APPROVED` | `:406-410` | 只有审核通过的活动才能发布 |
| → `RECRUITING` | `createUrgentActivity` | —（**跳过审核**） | `:451` | 仅组织者/管理员；组织者须已绑学院 |
| → `ONGOING` | `startActivity` | `RECRUITING` 或 `PUBLISHED` | `:467-472` | 只有已发布的活动才能开始 |
| → `COMPLETED` | `completeActivity` | `ONGOING` | `:484-488` | 只有进行中的活动才能完成 |
| → `ARCHIVED` | `archiveActivity` | `COMPLETED` | `:501-505` | 只有已完成的活动才能归档 |
| → `CANCELLED` | `cancelActivity` | 除 `CANCELLED`、`ARCHIVED` 外任意 | `:521-526` | 活动状态不允许取消 |

**自动流转**：`volunteer-backend/volunteer-activity/src/main/java/com/volunteer/activity/service/ActivityStatusTask.java` 每天 0 点执行（`@Scheduled(cron = "0 0 0 * * ?")` + `@SchedulerLock`）：

- `RECRUITING` / `PUBLISHED` → `ONGOING`（到达开始时间，`:69-87`）
- `ONGOING` → `COMPLETED`（到达结束时间，`:99-103`）
- `COMPLETED` → `ARCHIVED`（`:116-120`）

因此"手动开始/完成/归档"接口与定时任务**并存**：定时任务是兜底，手动接口用于提前推进。

**两个与状态机有关的事实**：

1. `PUBLISHED` 状态被 `startActivity` 接受，但**没有任何代码把它设为当前状态**——它只会出现在历史数据或由批量导入写入（`ActivityImportServiceImpl.java:253-255` 接受 `RECRUITING` / `PUBLISHED` / `APPROVED`）。可以视为保留状态。
2. `createUrgentActivity` 是**绕过审核的应急通道**：直接从创建跳到 `RECRUITING`，并打上 `is_urgent = true`、`urgent_level = "HIGH"`、写入 `published_time`（`:451-455`）。仅组织者（须绑学院）或管理员可调用。

### 2.3 参与闭环：报名 → 考勤 → 时长 → 激励 → 报表

这是平台的主价值链，跨 5 个模块。各环节的落库与状态：

| 环节 | 落库 | 状态取值 | 关键约束 |
|---|---|---|---|
| 报名 | `activity_registration` | `PENDING` / `APPROVED` / `REJECTED` / `CANCELLED` | 需 `access_level=1`（已绑学号）+ 档案完整（否则 HTTP 460）；活动须处于 `RECRUITING` / `PUBLISHED` / `ONGOING`（`ActivityService.java:725-727`） |
| 组队 | `team` / `team_member` | — | 建队需已绑学号 |
| 签到 | `attendance` | `PENDING` / `PENDING_AUDIT` / `APPROVED` / `REJECTED` | 活动状态须为 `RECRUITING` / `ONGOING` / `PUBLISHED`（`AttendanceService.java:103-105`）；`ARCHIVED` 活动禁止一切考勤操作（`:219`、`:538`、`:607`、`:676`） |
| 位置校验 | 同上 | — | `attendance.max-distance-meters` 默认 500 米，由 `GeoLocationService` 判定 |
| 补签 | `attendance` | `PENDING_AUDIT` → 审核通过/拒绝 | 组织者审核 |
| 时长 | `user_duration` | — | 活动完成后入账；争议走 `duration_dispute` |
| 激励 | `user_credit` / `credit_transaction` / `medal` / `user_medal` / `daily_task` / `user_task_record` | 流水类型 `EARN` / `CONSUME` | 人工调账仅 ADMIN（`/api/credit/add`、`/consume`） |
| 报表 | 读模型 + `export_task` | 导出任务异步 | Excel（POI）/PDF（iText） |

**事件驱动解耦**：报名、考勤等动作会发布领域事件，由监听器异步处理通知与统计，避免主流程阻塞：

| 事件 | 发布方 | 监听方 |
|---|---|---|
| `ActivityRegistrationEvent` | `volunteer-activity` | `ActivityBusinessEventListener`（`volunteer-report`） |
| `ActivityEvent` | `volunteer-activity` | `ActivityEventListener`（`volunteer-notification`） |
| `AttendanceEvent` | `volunteer-attendance` | `AttendanceBusinessEventListener`（`volunteer-report`） |

### 2.4 角色协作

五个角色（`ADMIN` / `ORGANIZER` / `COLLEGE_ADMIN` / `AUDITOR` / `VOLUNTEER`）的完整能力边界与判定链路见《角色功能详细文档》。设计上的协作关系是：

- **ADMIN** 跨学院，负责用户、角色、学院绑定、系统配置、考勤失信处置与人工调账。
- **ORGANIZER** 是业务主力，但被 `validateCollegeAccess` 限制在本院（`ActivityService.java:1025-1046`）。
- **COLLEGE_ADMIN** 设计上审核本院活动；活动写操作端点的注解只认 `ORGANIZER`，所以其写能力实际被注解层挡住（详见《角色功能详细文档》§5.4）。
- **AUDITOR** 无专属注解，靠 Service 内 `requireAuditPermission`（`ActivityService.java:1001-1018`）获得审核能力。
- **VOLUNTEER** 需先绑定学号（`access_level` 0→1）才能报名与签到，这是"访客→完整用户"的分界线。

## 三、系统架构

### 3.1 分层

```
┌─────────────────────────────────────────────────────────┐
│ 表现层  volunteer-frontend（uni-app + Vue 3 + Pinia）     │
│   pages / api / stores / utils(请求封装)                  │
└───────────────┬─────────────────────────────────────────┘
                │ HTTP（JSON，Authorization: Bearer）
┌───────────────▼─────────────────────────────────────────┐
│ 接入层  Nginx（可选，docker-compose.yml）                 │
│   / → 静态产物   /api /ws /swagger* → backend:8081        │
└───────────────┬─────────────────────────────────────────┘
┌───────────────▼─────────────────────────────────────────┐
│ 认证与访问控制  JwtAuthenticationFilter → SecurityConfig  │
│   → AccessControlInterceptor（@RequiresPermission/Access）│
│   → RateLimitInterceptor / ProfileCompletenessInterceptor │
└───────────────┬─────────────────────────────────────────┘
┌───────────────▼─────────────────────────────────────────┐
│ 应用层  Controller（37 个） → Service（49 个）             │
│   事务边界在 Service；Controller 只做参数绑定与结果包装     │
└───────────────┬─────────────────────────────────────────┘
┌───────────────▼─────────────────────────────────────────┐
│ 领域/持久层  MyBatis-Plus Mapper（63 个，纯注解）          │
│   Entity（65 个） / DTO（18 个） / MyMetaObjectHandler     │
└───────────────┬─────────────────────────────────────────┘
┌───────────────▼─────────────────────────────────────────┐
│ 基础设施  MySQL 8 · Redis 7 · MinIO · Flyway · 大模型 API │
└─────────────────────────────────────────────────────────┘
```

### 3.2 一次请求的完整链路

以"组织者发布活动"为例：

1. Nginx 收到 `POST /api/activity/publish/12`，按 `location /api` 转发到 `backend:8081`（前缀原样透传，因为 `proxy_pass` 未带路径部分）。
2. `JwtAuthenticationFilter` 解析 `Authorization` 头，把 `userId`、`username` 写入 request 属性。
3. `SecurityConfig` 判定：该路径不在白名单 → 要求已认证（否则 401）。
4. `AccessControlInterceptor.preHandle` 载入 `SysUser` 写入 `currentUser` / `currentCollegeId`，读取方法上的 `@RequiresAccess(value="organizer", requireStudentId=true)` → 校验角色与学号（不通过则 403）。
5. 限流与档案门控拦截器按路径匹配生效（发布接口只落在限流覆盖范围 `/api/activity/**` 内）。
6. `ActivityController` 从 `@RequestAttribute` 取 `userId`，调用 `ActivityService.publishActivity`。
7. Service 内三次校验：活动存在 → 归属（`validateOwner`）→ 学院（`validateCollegeAccess`）→ 状态须为 `APPROVED`。
8. 更新状态为 `RECRUITING`、写 `published_time`，调用 `activityCacheService.clearActivityCache(id)` 清缓存。
9. 返回 `Result.success(...)`，异常由 `GlobalExceptionHandler` 统一转成 JSON。

### 3.3 模块划分与依赖

根 `pom.xml` 的 `<modules>` 共 **8 条**（`pom.xml:44-53`），全部位于 `volunteer-backend/` 下，最终由 `volunteer-server` 打成一个可执行 jar：

```
volunteer-server   ← 启动类 + 全部配置 + resources（唯一有 yml/db 脚本的模块）
      ├── volunteer-report      （依赖 activity, attendance, ai）
      │      ├── volunteer-activity   （依赖 auth, notification）
      │      │      ├── volunteer-auth        ← SecurityConfig / JWT / 拦截器
      │      │      ├── volunteer-notification（WebSocket / 站内信 / 短信）
      │      │      └── volunteer-common      ← Result / 枚举 / 异常 / MinIO / 加密
      │      └── volunteer-attendance （依赖 activity, ai）
      └── volunteer-ai          （依赖 activity；LangChain4j）
```

依赖分层（无环）：

| 层 | 模块 | 被谁依赖 |
|---|---|---|
| L0 基础设施 | `volunteer-common` | 全部 |
| L1 能力 | `volunteer-auth`、`volunteer-notification`、`volunteer-ai` | activity / attendance / report / server |
| L2 领域 | `volunteer-activity`、`volunteer-attendance` | report、server |
| L3 聚合 | `volunteer-report` | server |
| 顶层 | `volunteer-server` | —（依赖全部 7 个模块） |

`volunteer-activity` 被 6 处引用，是最被复用的领域模块；`volunteer-ai` 被 `attendance`（补签分析）与 `report`（诊断、推荐）复用。

### 3.4 各模块职责

| 模块 | Java 文件数 | 职责 | 关键包 |
|---|---|---|---|
| `volunteer-common` | 26 | 统一返回体、分页、全局异常、基础实体、枚举、MinIO 存储抽象、AES 加密工具、操作日志切面 | `result`、`exception`、`entity`、`enums`、`storage`、`interceptor`、`aspect` |
| `volunteer-auth` | 38 | 认证（JWT）、授权（注解 + 拦截器）、验证码、用户/角色/权限/学院管理 | `config`、`filter`、`interceptor`、`service`、`mapper` |
| `volunteer-activity` | 34 | 活动全生命周期、报名、组队、活动模板、批量导入、状态定时任务 | `controller`、`service`、`task`、`event` |
| `volunteer-attendance` | 10 | 签到、位置校验、补签分析、失信记录、时长 | `service`、`entity`、`event` |
| `volunteer-notification` | 13 | 站内信、公告、WebSocket 推送、短信抽象（`SmsService` + console 实现） | `service`、`event` |
| `volunteer-report` | 140 | **业务最重的模块**：报表、统计看板、导出、信用、时间银行、技能、培训、推荐、诊断、评价、课程表、系统配置、操作日志、争议处理 | `controller`(21)、`service`(20)、`mapper`(44)、`entity`(45) |
| `volunteer-ai` | 11 | 基于 LangChain4j 的问答、推荐、草稿生成、内容生成、知识库、排班建议、情感分析、总结 | `config`、`service` |
| `volunteer-server` | 12 | 启动类、全部 Spring 配置、文件上传下载接口、MinIO 服务 | `config`、`controller`、`service` |

**一个值得注意的结构问题**：名为 `report`（报表）的模块实际承载了信用、时间银行、技能认证、培训、推荐、诊断、评价、课程表、系统配置、操作日志等**十余个业务域**，占全部主源码的 49%（140/284）。它既不是纯粹的报表模块，也不是单一业务域，而是"其余业务的集合"。这是当前架构里最明显的边界模糊处，演进方向是按业务域拆分（见 §10）。

### 3.5 关键约定

1. **接口前缀**：项目**没有设置** `server.servlet.context-path`，所有业务接口的 `/api` 前缀来自各 Controller 自己的 `@RequestMapping`。唯一例外是 Actuator，通过 `management.endpoints.web.base-path=/api/actuator` 显式对齐。因此 Swagger 系列路径（`/v3/api-docs`、`/swagger-ui/**`、`/doc.html`）**不带 `/api`**。
2. **统一返回体**：所有接口返回 `Result<T>`（`code` / `message` / `data`）。**业务失败也是 HTTP 200**，只把 `code` 置为非 200；只有参数、状态、权限、限流等错误才用非 200 的 HTTP 状态码。异常到响应的完整映射表见《后端接口API文档》§1.5。
3. **持久层无 XML**：全部 63 个 Mapper 使用 MyBatis-Plus 注解与 `LambdaQueryWrapper`，全仓库 `src` 下没有任何 `.xml`（唯一的 XML 是 8 个 `pom.xml`）。修改 SQL 时不要去找 `resources/mapper/`。
4. **服务层不拆接口与实现**：49 个 Service 中只有 1 个 `ServiceImpl`（`ActivityImportServiceImpl`），其余全是"类即实现"。
5. **主键策略**：全部实体使用 `@TableId(type = IdType.AUTO)`，与 DDL 的 `BIGINT AUTO_INCREMENT` 一致；**不可改为雪花 ID**，否则种子数据里硬编码的 id（权限 1–15、角色 1–5、用户 1–8）与 `sys_user_role` 的映射会失配（详见《数据库设计文档》§1.1）。
6. **逻辑删除**：70 张表中 23 张有 `deleted` 字段（`@TableLogic`），47 张靠业务状态字段表达删除（如 `status`、`activity.status = CANCELLED`）。
7. **公共字段自动填充**：`volunteer-common/.../config/MyMetaObjectHandler.java` 负责 `create_time` / `update_time`（以及部分表的 `create_by`）。

## 四、技术选型

### 4.1 后端

| 技术 | 版本 | 选它的原因 |
|---|---|---|
| JDK | 17 | Spring Boot 3 的最低要求；LTS |
| Spring Boot | 3.3.2 | 统一依赖管理（parent BOM），内嵌 Tomcat，Actuator 开箱可用 |

### 4.5 技术决策记要

| 决策 | 选择 | 原因 |
|---|---|---|
| ShedLock 版本锁死 5.16.0 | 不用 6.x/7.x | ShedLock 5.16.0 对应 Spring 6.1.12 / Spring Boot 3.3.3 / JDK 17；**6.x 要求 Spring Boot 3.4+，7.x 要求 Spring Boot 4.x + Spring 7**，与本项目的 Spring Boot 3.3.2（Spring Framework 6.1.x）不兼容。升级 Boot 才能升 ShedLock（`pom.xml:35-40` 注释） |
| 锁提供者用 JDBC 而非 Redis | `JdbcTemplateLockProvider` + `shedlock` 表 | 复用已有的 MySQL 连接，不额外依赖 Redis 的可用性；定时任务是低频操作，JDBC 开销可接受 |
| 认证无状态 JWT 而非 Session | `SessionCreationPolicy.STATELESS` + `JwtAuthenticationFilter` | 便于水平扩容与前后端分离；代价是角色变更需等令牌过期（24 小时）才在客户端生效 |
| 角色判定查关系表 | `sys_user_role JOIN sys_role` | 权威性优先：`sys_user.role_code` 是冗余列，存在未回填的情况（admin 即为例）。代价是每次判定两次查询，无缓存 |
| 细粒度权限用注解 + Redis 缓存 | `@RequiresPermission` + `UserPermissionService`（TTL 5 分钟） | 设计上是替代角色字符串硬编码的方案；**但生产代码尚未接入任何接口**，见《角色功能详细文档》§5.1 |
| 业务异常返回 HTTP 200 | `GlobalExceptionHandler` 对 `BusinessException` 固定 200 + `code` | 让前端只需判断 `code`，避免把"业务失败"当成"网络/服务错误"处理 |
| 密码 BCrypt strength 12 | `BCryptPasswordEncoder(12)` | 高于默认 10，兼顾强度与登录延迟 |
| 敏感字段 AES-GCM 加密工具 | `EncryptUtil` + `@Encrypted` + MyBatis `EncryptInterceptor` | 设计上用于身份证号等敏感字段；**当前没有任何实体字段标注 `@Encrypted`**，能力处于待用状态 |
| 限流按 IP+URI 固定窗口 | Redis `INCR` + 1 分钟过期，5 次/分钟 | 先自增再判断，避免"读—判—写"竞态；Redis 异常时**放行**（fail-open），避免限流组件故障导致全站不可用 |
| 导出走异步任务 | `export_task` 表 + `AsyncConfig` | 大报表生成耗时长，同步返回会超时；任务状态供前端轮询 |
| 事件驱动通知 | Spring 事件 + 监听器 | 通知/统计失败不应回滚主业务事务 |
| 数据表 70 张不拆库 | 单库 | 规模可控，跨域查询（报表/诊断）远多于写入隔离需求 |

## 五、核心模块设计

### 5.1 认证与权限（`volunteer-auth`）

- **登录**：`AuthService.login`（`volunteer-backend/volunteer-auth/src/main/java/com/volunteer/auth/service/AuthService.java:52-117`）按标识分流——`isPhoneNumber` 命中时按 `phone` 查；否则先按 `student_id` 查，查不到再按 `username` 查（`:58-75`）。依次校验：用户存在（"用户不存在，请先注册"）→ 未被禁用（"用户已被禁用"，`status == 0`）→ 未锁定（"登录失败次数过多，请稍后再试"）→ 滑块（开关开启时）→ 口令。成功后清除失败计数、签发 JWT，并用 `resolveAccessLevel` 计算 `visitor` / `full`（`:114`）。另有 `refreshToken`（`:119-134`）用于换发令牌。
- **失败锁定**：失败计数键为 `login:fail:{登录标识}`（`:297`），阈值 `captcha.login-fail-lock-threshold` 默认 **3** 次，锁定时长 `captcha.login-fail-lock-minutes` 默认 **5** 分钟（`:46-50`、`:296-310`、`:330-339`）；阈值 ≤ 0 时关闭锁定（`:301`、`:331`）。代码注释说明计数只按登录名累加，未叠加 IP。
- **注册**：新用户 `access_level = VISITOR(0)`（`AuthService.java:171`）；口令强度要求 8–32 位且含大写、小写、数字、特殊字符（`validatePasswordStrength`，`:182-205`）。
- **绑定学号**：`bindStudentId`（`:207-240`）校验"未绑定过""口令正确""学号未被占用"，成功后设 `student_id` 并把 `access_level` 升为 `FULL_ACCESS(1)`。
- **授权**：见《角色功能详细文档》§1。
- **滑块验证码**：`CaptchaService` + `CaptchaController`（`/api/captcha/**`，免登录）。登录是否强制由 `captcha.required` 控制，**默认 false**（`:43-44`）；开启后缺 `captchaId` / `sliderX` 报"请先完成滑块验证"，校验不过报"滑块验证失败"（`:90-99`）。注意 `application*.yml` 中**没有任何 `captcha.*` 配置项**，因此运行期一律取代码默认值——而 `AuthService.java:29` 的类注释声称"登录主流程强制串联 captcha 校验"，与"默认关闭"的开关不一致。

### 5.2 活动管理（`volunteer-activity`）

- 创建时**同名校验**（同一组织者下、非 `CANCELLED` 的同名活动拒绝，`:300-307`）、人数上限校验（`:309-311`）。
- 活动范围由 Service 决定：组织者创建时强制 `COLLEGE` + 本人 `college_id`；管理员可指定 `UNIVERSITY`（此时 `college_id` 置 null）或 `COLLEGE`（必须给 `collegeId`）（`:423-448`）。
- **可见性**（`:243-262`）：未绑学号的用户只能看到 `UNIVERSITY` 活动；完整用户可加看本学院 `COLLEGE` 活动。
- **缓存**：`ActivityCacheService` 缓存活动数据，所有写操作后调用 `clearActivityCache()` / `clearActivityCache(id)`。
- **变更留痕**：`ActivityChangeLogService` 记录状态与内容变更，落到 `activity_change_log`。
- **批量导入**：`ActivityImportService` / `ActivityImportServiceImpl`（全项目唯一的 `ServiceImpl`），支持预览（`ImportPreviewDTO`）→ 确认（`ImportConfirmRequest`）→ 结果（`ImportResultDTO`）三步，日志落 `activity_import_log`。
- **定时任务**：`ActivityDeadlineTask` 每小时检查临近截止的活动并提醒（`cron = "0 0 * * * ?"`），每天 1 点检查名额不足的活动（`cron = "0 0 1 * * ?"`）；两者都有 `@SchedulerLock`。

### 5.3 报名与组队

- 报名端点 `POST /api/activity/{id}/register` 需要 `requireStudentId`，且活动状态须为 `RECRUITING` / `PUBLISHED` / `ONGOING`（`:725-727`）；档案不完整会被 460 拦下。
- 报名记录状态 `PENDING` / `APPROVED` / `REJECTED` / `CANCELLED`，组织者通过 `/api/registration/{id}/approve`、`/reject` 审核。
- 组队：`TeamController` 提供建队、入队、成员管理；建队端点需 `requireStudentId`（`TeamController.java:27-28`）。
- 报名当前人数存 `activity.current_participants`，参与人数上限校验基于该字段。

### 5.4 考勤与时长（`volunteer-attendance`）

- 签到流程：组织者用 `/api/attendance/qrcode/{activityId}` 生成二维码 → 志愿者扫码 → `AttendanceService` 校验活动状态（`:103-105`）、是否已签到、时间窗口与位置距离（`GeoLocationService`，阈值 `attendance.max-distance-meters` 默认 500 米）。
- 补签：提交后状态 `PENDING_AUDIT`，由组织者 `/api/attendance/supplementary/{id}/approve` / `reject` 审核；`SupplementaryAnalysisService` 提供辅助分析。
- `ARCHIVED` 活动禁止一切考勤修改（`:219`、`:538`、`:607`、`:676`）。
- 失信记录 `violation_record`：由管理员处置（`/api/attendance/violation/**`）。
- 时长：`user_duration` 记录服务时长，争议走 `duration_dispute`（`DurationDisputeService`），审批走 `/api/duration/{id}/approve`（仅 ADMIN）；外部平台时长由 `ExternalDurationService` 导入与审核。

### 5.5 消息通知（`volunteer-notification`）

- 三种通道：站内信（`user_message`）、系统公告（`system_announcement`）、WebSocket 实时推送（`WebSocketPushService` + `volunteer-server` 的 `WebSocketConfig`）。
- 短信走抽象：`SmsService` 接口 + `DefaultSmsService`；开发环境 `notification.sms.console-enabled=true` 把验证码打印到日志，生产环境关闭。
- 消息模板存 `message_template`，由 `MessageTemplateMapper` 读取。
- 通知由事件驱动触发（见 §2.3 的事件表），保证主业务不被通知失败拖垮。

### 5.6 报表与导出（`volunteer-report`）

- 21 个 Controller 覆盖：报表（个人/组织）、统计、看板（Dashboard）、导出、信用、时间银行、技能、培训、评价、推荐、诊断、地图、待办、系统配置、操作日志、外部时长、时长争议、课程表。
- 导出：`ExportTaskService` + `export_task` 表做异步任务，`BigDataExcelExporter` / `ExcelStyleUtil` 负责 Excel 样式与大数量写入，PDF 用 iText（`itext-asian` 保证中文）。
- 诊断类功能（`DiagnosisService`、`activity_health` / `activity_metric` / `diagnosis_report` / `improvement_suggestion`）对活动健康度做量化与建议生成。
- 统计与推荐读接口对全体登录用户开放，写与管理接口受角色限制。

## 六、课程表模块

### 6.1 定位与现状

课程表用于**「学生的课表」与「志愿活动时间」的冲突检测**：录入本学期课程后，报名前可判断某个时间段是否与上课冲突，或从一批活动中筛出空闲可参加的那些。

它的代码位于 `volunteer-report` 模块（`ScheduleController` + `ScheduleService`），表结构5 张表，**共 14 个接口**。

**现状（重要）**：该模块目前**只有后端**。

- 前端 `volunteer-frontend/src` 中搜索 `schedule` 只命中 `src/api/ai.js:60,65,70,75` 的 `/api/ai/schedule/*`（属于 `volunteer-ai` 的 AI 排班，与本模块无关）；搜索 `api/schedule`、`课表`、`排课`、`weekType`、`colorCode`、`dayOfWeek` 均无命中；`src/pages` 的 15 个页面里没有课表页，`src/api` 的 21 个文件里没有 `schedule.js`。
- 因此"视觉规则"（格子颜色）只存在于后端：空格子为 `ColorCode.EMPTY`，每周课程为 `RED`，单双周课程为 `YELLOW`。

### 6.2 数据模型

|---|---|---|---|

### 6.4 核心算法

**(a) 周次匹配**（`volunteer-backend/volunteer-report/src/main/java/com/volunteer/report/service/ScheduleService.java:182-199`）：

```java
private boolean isCourseActiveInWeek(CourseSchedule course, Integer week) {
    if (week == null) return true;
    if (week < course.getStartWeek() || week > course.getEndWeek()) {
        return false;
    }
    String weekType = course.getWeekType();
    if (WeekType.EVERY.getCode().equals(weekType)) {
        return true;
    } else if (WeekType.SINGLE.getCode().equals(weekType)) {
        return week % 2 == 1;
    } else if (WeekType.DOUBLE.getCode().equals(weekType)) {
        return week % 2 == 0;
    }
    return true;
}
```

规则：先判周次是否落在 `[startWeek, endWeek]` 闭区间内；再按单双周判定，**单双周 = 周次序号的奇偶**（单周为奇数周、双周为偶数周）。`week` 为 null 或 `weekType` 未知时一律视为有效。

**(b) 时间冲突判定**（`ScheduleService.java:302-304`）：

```java
private boolean hasTimeOverlap(LocalTime start1, LocalTime end1, LocalTime start2, LocalTime end2) {
    return start1.isBefore(end2) && end1.isAfter(start2);
}
```

用的是**严格不等式**，所以首尾相接（10:10 结束 vs 10:10 开始）**不算冲突**。

调用侧（`checkConflict` `:267-300`、`getConflictingCourses` `:306-347`）：取活动开始时间的 `DayOfWeek`（周一=1…周日=7，与 `day_of_week` 语义一致）→ 取当前周（无活跃学期则按第 1 周）→ 逐门课程先做周次匹配、再比星期几、再从 `time_slot_config` 取该节次的起止时间（`LocalTime.parse`）做重叠判定。

**(c) 节次到时间的换算**：代码里没有换算，全部来自 `time_slot_config` 配置表。种子数据（`V1__baseline_full_schema.sql:2056-2061`）：

| period | start_time | end_time | duration_minutes |
|---|---|---|---|
| 1 | 08:30 | 10:10 | 100 |
| 2 | 10:30 | 12:10 | 100 |
| 3 | 14:30 | 16:10 | 100 |
| 4 | 16:30 | 18:10 | 100 |
| 5 | 19:30 | 21:10 | 100 |

读取路径：`TimeSlotConfigMapper.findActiveSlots()`（`WHERE status = 1 ORDER BY sort_order ASC, period ASC`）、`findByPeriod()`（`WHERE period = #{period} LIMIT 1`）。

**(d) 网格构建**（`getScheduleGrid` `:130-180`）：先构造 7 天 × 5 节的空格子（`DAY_NAMES` = 周一…周日、`PERIOD_NAMES` = 第1节…第5节），格子颜色置为 `EMPTY`；再取本人全部有效课程，用 `isCourseActiveInWeek(course, week)` 过滤后填入 `course` 与颜色。**同一格子里多门课会互相覆盖**（后遍历到的胜出，`:165-167`）。

**(e) 冲突筛选**（`filterActivitiesWithoutConflict` `:374-386`）：对每个活动调用 `checkConflict`，**只保留无冲突的活动**返回。

| 规则 | 实现位置 | 说明 |

### 6.6 与活动冲突筛选的联动

- 入口是 `/conflict/check`（返回 `hasConflict`、`conflictCount`、`conflicts`）与 `/conflict/filter`（入参 `Map<Long, String[]>`，即 活动 ID → `[开始时间, 结束时间]`；返回 `filteredActivities`、`totalActivities`、`availableActivities`）。
- 调用链：`ScheduleController` → `ScheduleService.checkConflict` / `getConflictingCourses` → `CourseScheduleMapper.findByUserId` + `TimeSlotConfigMapper.findByPeriod` + `WeekConfigMapper.findActiveSemester`。
- **前端与报名流程都没有调用 `/api/schedule/conflict/*`**——这条能力目前只在后端可用，报名页不会自动拦截冲突。

### 6.7 已知问题

1. **冲突判定只用"当前周"**：`checkConflict` 先取 `week_config.current_week`（无活跃学期按第 1 周），再逐门课用 `isCourseActiveInWeek(course, currentWeek)` 过滤。**活动日期落在学期的第几周完全被忽略**，日期中的年/月/日也不参与判定，只取"星期几 + 时刻"。因此"下个月某天的活动是否与课冲突"这类跨周判断结果不准确。
2. **`/week-courses` 缺少单双周过滤**：它走 `CourseScheduleMapper.findByUserIdAndWeek`（`CourseScheduleMapper.java:19-23`），SQL 只过滤 `start_week <= week AND end_week >= week`，`getUserScheduleByWeek`（`:46-48`）也没有调用 `isCourseActiveInWeek` → 该接口会返回单/双周不匹配的课程。只有 `/grid` 与冲突检测做了奇偶过滤。
3. **`activity_conflict_check` 表不会被写入**：`recordConflictCheck`（`:349-372`）实现完整，但**全仓库没有任何调用方**；`ActivityConflictCheckMapper` 的 4 个查询方法同样无调用方。
4. **无配置管理接口**：节次时间与学期周次只能直接改库。
5. **前端缺失**：没有课表页面，颜色/网格等视觉规则的消费方还不存在。
6. **后端批量导入不解析 Excel**：`/import` 接收的是已经解析好的 `List<CourseSchedule>`，Excel 列映射代码在后端不存在（应在客户端实现，但客户端页面也未实现）。

## 十、已知缺口与演进方向

以下均为**代码现状**，不是设计意图；按影响排序。前三条与权限相关，详见《角色功能详细文档》§5。

1. **细粒度权限未接入**：`@RequiresPermission` 与 `UserPermissionService`（15 个权限点 + Redis 缓存）在主源码零调用，实际鉴权靠 `@RequiresAccess` 角色字符串。
2. **文件与导出接口无访问控制**：`/api/file/**`、`/api/export/**` 无注解、不在白名单 → 任何登录用户可下载任意导出文件。
3. **待审列表未按权限过滤**：`GET /api/activity/audit/page` 任意登录用户可读。
4. **模块边界模糊**：`volunteer-report` 承载十余个业务域、占 49% 源码。演进方向：把信用/时间银行/技能/培训/课程表拆成独立模块，`report` 只留报表与统计。
5. **`PUBLISHED` 状态实际不可达**：只有 `startActivity` 接受它，没有代码设置它。
6. **前端角色链路断裂**：登录响应不返回角色，前端角色恒为 `VOLUNTEER`，管理端页面无角色门控。
7. **角色判定无缓存**：每个受保护请求都要查 `sys_user_role` + `sys_role`。
8. **无角色码常量类**：角色字符串字面量散落在 3 个 Service 与 2 个测试中，拼错不会被编译期发现。
9. **`@Encrypted` 能力未启用**：`EncryptInterceptor` 与 `EncryptUtil` 已就绪，但没有任何实体字段标注该注解。
10. **课程表冲突判定忽略活动所在周**，`/week-courses` 缺少单双周过滤，`activity_conflict_check` 无写入方（§6.7）。
11. **`access_level` 列注释与代码语义相反**（`V1__baseline_full_schema.sql` 中注释为"0-管理员…"，代码为"0-访客"）。
12. **`sys_permission` 种子数据的 `parent_id` 有误**：`report:personal`(12)、`report:organization`(13) 的父节点是 10（`attendance:supplement`）而非 11（`report`）。
13. **Nginx 未设置 `client_max_body_size`**：默认 1 MB 会先于后端的 50 MB 上限拒绝大文件上传（经 Nginx 时）。
14. **Docker 首次构建未做端到端验证**：镜像与配置已就绪，但完整的 `up --build` 尚未在本项目上跑通（用户明确要求暂不部署测试）。
