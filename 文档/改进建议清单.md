## 附二、第二轮补修记录

### 2.1 第二梯队授权覆盖（原报告 P0-4 此前并未真正落盘）

在文档初稿完成后做授权覆盖复核时发现，**原报告的「P0-4 零权限注解接口」并未在本轮真正落到代码上**：以下控制器此前仍然只有登录态约束（`AccessControlInterceptor.preHandle` 在方法上找不到注解时直接 `return true`）。本轮已补齐，并新增签到时间窗配置化。

| 文件 | 补上的注解 | 理由 |

### 2.2 第三梯队：签到时间窗配置化（P2-6）

**签到时间窗配置化（第三梯队 P2-6）**：`AttendanceService.validateCheckInAllowed` 原为 `minusMinutes(30)` / `plusHours(2)` 硬编码，而 `system_config` 的种子值是 `attendance.check_in_advance=30`、`attendance.check_in_delay=60`（分钟）—— 延迟窗比设计值宽一倍且改配置无效。现改为读 `attendance.check-in-advance-minutes`（默认 30）与 `attendance.check-in-delay-minutes`（默认 60），理由与后续统一配置入口的建议见上表 D-9。

### 2.3 Actuator 健康详情默认关闭（原报告 P2-11）

`management.endpoint.health.show-details` 原默认值为 `always`（`application.yml` 与 `application-dev.yml` 各一处），而 `/api/actuator/health` 被 `SecurityConfig.java:60-62` 显式匿名放行 —— 未认证访问者可直接读到数据库类型与校验语句、服务器绝对路径与磁盘容量、Redis 版本（实测已复现）。现两处默认值统一改为 `never`（环境变量 `MANAGEMENT_ENDPOINT_HEALTH_SHOW_DETAILS` 仍可临时覆盖为 `always`）。整体 `status` 字段不受该开关影响，故 `Dockerfile` 的 `HEALTHCHECK`（`curl -fsS .../api/actuator/health`）与编排的 `service_healthy` 判定照常工作；文档 `项目启动与配置指南.md:138,166` 与 `后端接口API文档.md:767` 已同步。

## 附三、权限注解复核时连带发现的真实缺陷（R-3 / R-4）

在补齐上面的授权注解时做运行时验证，连带发现并修复了两个**此前未列出的真实缺陷**：

| 编号 | 文件与行号 | 问题 | 根因与影响 | 修复 |
|---|---|---|---|---|
| R-3 | `volunteer-backend/volunteer-common/src/main/java/com/volunteer/common/exception/GlobalExceptionHandler.java`（原 `:117-122` 只有 `NoHandlerFoundException` 处理器） | **访问不存在的接口返回 HTTP 500「系统繁忙」而不是 404** | Spring Boot 3 中「路径无 Controller 匹配」抛出的实际是 `NoResourceFoundException`（静态资源兜底），而原代码只处理 `NoHandlerFoundException` —— 后者在默认配置（`spring.mvc.throw-exception-if-no-handler-found=false`）下**永远不会被抛出**，于是请求落到 `Exception` 兜底分支返回 500。实测证据：`GET /api/auth/me`、`GET /api/ai/agent/health`、`GET /api/schedule/today` 全部返回 `HTTP 500 {"code":500,"message":"系统繁忙，请稍后重试"}`，日志为 `NoResourceFoundException: No static resource api/auth/me` | 新增 `@ExceptionHandler(NoResourceFoundException.class)` + `@ResponseStatus(HttpStatus.NOT_FOUND)`，返回 `Result.error(404, "接口不存在")`；同时把原有 `NoHandlerFoundException` 处理器的 body code 由 500 改为 404，保持 HTTP 状态码与 body code 一致。实测：四个不存在的路径现在都返回 `HTTP 404 {"code":404,"message":"接口不存在"}`，存在的接口仍 200 |
| R-4 | `volunteer-backend/volunteer-activity/src/main/java/com/volunteer/activity/service/impl/ActivityImportServiceImpl.java:607`（原实现） | `checkIsAdmin(SysUser)` 用 `user.getAccessLevel() == 0` 判断管理员，**语义完全颠倒** | 项目内 `AccessLevelEnum` 定义 `VISITOR(0)` / `FULL_ACCESS(1)`，而 `AuthService` 判定完整访问用的是 `FULL_ACCESS.getCode()`（=1）。因此 `accessLevel == 0` 实际命中**访客**：`validatePermission`（`:260-273`）的 `if (!isAdmin && !isOrganizer) throw` 会让普通用户（access_level=1）被拒、却让访客放行，而真正的管理员走的是 `roleCode` 而非 accessLevel，**在导入参与者这项上反而不被识别为管理员**。同文件 `checkIsOrganizer` 用的就是 `roleCode`，说明是复制粘贴时写错字段语义 | 改为与 `ActivityService.checkIsAdmin`（`:981-983`）一致的角色判定：`return user != null && "ADMIN".equals(user.getRoleCode());`；并把同方法内的 `!activity.getCollegeId().equals(currentUser.getCollegeId())` 改为 `!Objects.equals(...)`，避免校级活动 `college_id IS NULL` 时抛 NPE |

**说明**：`access_level` 字段在 DDL 注释（`V1__baseline_full_schema.sql:81`「0-管理员, 1-组织者, 2-完整用户, 3-访客」）与 Java 枚举（`AccessLevelEnum`：VISITOR=0/FULL_ACCESS=1）之间语义冲突，是上面 R-4 的土壤。当前真正的鉴权判定已统一走**角色码**（`ADMIN`/`ORGANIZER` 等）与 `AuthService.hasFullAccess()`，`access_level` 仅用于 `AuthController.java:95` 的展示字段，故不再有行为影响；但该字段的三方语义冲突仍建议清理（见 E-2）。
